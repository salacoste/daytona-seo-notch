# Сценарий 2. Сайт в разработке, уже что-то есть

**Ситуация:** есть часть кода/контента/макетов (свой проект или передача от
другой команды), публикации ещё нет. Цель — извлечь максимум из
существующего, закрыть пробелы брифа и выйти на запуск через гейт.

## Карта пути

```
Шаг 1           Шаг 2             Шаг 3              Шаг 4
Локальный   →   Бриф (только   →  Верстка-гейт   →   Запуск
разбор          пробелы) +        (Phase 1–2)
существующего   запросы
/daytona-       /daytona-         /daytona-          /daytona-
seo-notch-      seo-notch-        seo-notch-         seo-notch-
brief (B)       brief (A,C,D)     prelaunch          prelaunch (3)
                                  + треки аудита
```

## Шаг 1 — Локальный разбор существующего: `/daytona-seo-notch-brief` (стадия B)

Скилл сканирует папку проекта (read-only) по методу `references/local-scan.md`:

1. **Identity:** README/docs/лендинг-тексты → что за продукт, для кого, с
   каким обещанием; цены → сегменты.
2. **Инвентарь контента:** по каждому файлу (`.md/.mdx/.html/.astro/.jsx`) —
   H1, существующие title/meta (есть? уникальны? шаблонные?), объём, язык,
   флаги (черновики, дубли меты, нет дат/авторов).
3. **SEO-сигналы в коде:** JSON-LD в шаблонах, черновики sitemap/robots,
   canonical-логика, OG-компоненты, i18n-роутинг.
4. **Вердикт стека:** SSR/SSG/SPA (что ждать от индексируемости), CMS,
   подключённая аналитика.
5. **Нативная лексика** проекта → seed-запросы.

Артефакт: `brief-<slug>/local-scan.md` — каждый факт с указанием файла.

## Шаг 2 — Бриф только по пробелам + запросы: `brief` (стадии A, C, D)

1. Stage A спрашивает **только то, что не ответил скан** (поля брифа
   помечены `answered from code` vs «спросить»).
2. Stage C: пул = нативная лексика + бриф; гейт согласования `queries.md`.
3. Stage D: частотность (Keyword Planner / DataForSEO / Wordstat-флоу) —
   каждое число с тегом источника.
4. Сверка с существующим: какие уже свёрстаные страницы закрывают
   согласованные запросы, каких URL не хватает → дельта в IA.

## Шаг 3 — Достроить и загейтить: `/daytona-seo-notch-prelaunch` (Phase 1–2)

1. Экспортируйте `CLAUDE_SEO_LOCAL_TARGETS=localhost:<порт>` (или поднимите
   статикой: `cd dist && python3 -m http.server 4173`).
2. Phase 1: доведите существующие шаблоны до норм (title/meta/H1/schema/
   SSR/картинки); найденные сканом флаги — закрыть по списку.
3. Phase 2 — гейт:
   - `/daytona-seo-notch-audit http://localhost:<порт>`;
   - `/daytona-seo-notch-technical` — если аудит показал проблемы глубже;
   - `/daytona-seo-notch-schema <url>` — генерация недостающего JSON-LD;
   - `/daytona-seo-notch-sitemap generate`;
   - `/daytona-seo-notch-ai readiness`;
   - `/daytona-seo-notch-drift baseline` — база до запуска (дальше любые
     изменения команды видны как drift).
4. CI-гейт на PR — рецепт в `references/dev-workflow.md`.

## Шаг 4 — Запуск: `prelaunch` (Phase 3)

Тот же свитч, что и в сценарии 1. Особенности передачи/достройки:
- если заменяется старый сайт — редирект-карта 301 обязательна в гейте;
- если контент писала другая команда — прогнать `/daytona-seo-notch-content`
  на ключевых страницах (E-E-A-T, Who/How/Why) до гейта.

## Скиллы сценария (порядок)

`brief` (B→A→C→D) → `prelaunch` (0-дельта, 1–2) → `audit`/`technical`/
`schema`/`sitemap`/`ai`/`content` → `drift` → `analytics` → `page` (точечные
разборы).

## Частые ошибки

- Согласовывать запросы, не глянув в код (нативная лексика уже лежит в файлах).
- Аудит «когда выложим» — гейт ловит проблемы, пока они дешёвые.
- Дубли меты от шаблонной генерации — скан их подсветит; чинить в шаблоне,
  не постранично.
